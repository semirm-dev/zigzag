# zbridge

> Fully AI implemented, testing MVP.
> Next step: Complete manual (careful) rewrite.

Turn a Zig `export fn` surface into a Go module and a Python package — with the
native library already cross-compiled and embedded, so the people consuming it
never install Zig, never see a C compiler, and never know FFI is happening.

```
your c_api.zig  ──▶  zbridge  ──▶  bindings/go/      (go get)
                                   bindings/python/  (pip install)
                                   bindings/c/       (a plain .h)
```

Requires **Zig 0.16.0**.

---

## Quickstart

Write the API you want to export in one Zig file. Nothing zbridge-specific —
just `export fn` and `opaque {}`:

```zig
// src/c_api.zig
const digest = @import("digest.zig");

/// An opaque running counter.
pub const Counter = opaque {};

/// Allocate a counter. Returns null when the pool is exhausted.
export fn zcounter_new() ?*Counter { ... }

/// Release a counter.
export fn zcounter_destroy(c: *Counter) void { ... }

/// Mix `data[0..len]` into the digest; returns the new total byte count.
export fn zcounter_feed(c: *Counter, data: [*]const u8, len: usize) u64 { ... }

/// Write the running total through `out`. Returns false for a stale handle.
export fn zcounter_total(c: *Counter, out: *u64) bool { ... }
```

Add zbridge to your `build.zig.zon` and call it from your `build.zig`:

```zig
const zbridge = @import("zbridge");

pub fn build(b: *std.Build) void {
    _ = zbridge.addPortStep(b, .{
        .name = "zcounter",
        .root_source_file = b.path("src/c_api.zig"),
        .out_go = b.path("bindings/go"),
        .out_python = b.path("bindings/python"),
        .out_c_header = b.path("bindings/c"),
        .go_module_path = "github.com/you/zcounter-go",
    });
}
```

```sh
zig fetch --save git+https://github.com/you/zbridge#v0.1.0
zig build port
```

That one command parses the file, validates every signature, cross-compiles the
shared library for all five targets, and writes bindings you commit:

```go
c, err := zcounter.New()
defer c.Close()
total := c.Feed([]byte("hello"))
ok, n := c.Total()
```

```python
with zcounter.Counter.new() as c:
    total = c.feed(b"hello")
    ok, n = c.total()
```

A complete, working example lives in [`examples/zcounter/`](examples/zcounter/),
including the Go and Python consumer test suites CI runs on every push.

> **Naming tip.** zbridge strips the library name from each symbol before
> converting case, which is why `zcounter_feed` becomes `Feed()` / `feed()`
> above. Name your exports `<libname>_*` and the generated API reads the way
> you would have written it by hand; use some other prefix and you get
> `ZcCounterFeed` instead. zbridge warns when it notices the mismatch.

## Two front ends, one core

Parse → validate → generate → compile is implemented once. Both front ends call
it, so they produce byte-identical output for the same input.

### `build.zig` integration — recommended

`addPortStep` (above) registers a `zig build port` step. This is the primary
path because it hands module resolution to *your* build graph: if your exported
code reaches into a named `build.zig.zon` dependency, declare the mapping and it
just works.

```zig
_ = zbridge.addPortStep(b, .{
    .name = "zpdf",
    .root_source_file = b.path("src/c_api.zig"),
    .imports = &.{
        .{ .name = "zigimg", .dependency = "zigimg", .module = "zigimg" },
    },
    .targets = &.{ "linux_x86_64", "macos_aarch64", "windows_x86_64" },
    .link_libc = false,
    .out_go = b.path("bindings/go"),
    .out_python = b.path("bindings/python"),
});
```

### CLI — for one-off and scripted use

```sh
zbridge port --input src/c_api.zig --name zcounter \
             --out-go bindings/go --out-python bindings/python

zbridge generate --input src/c_api.zig --name zcounter --out-go bindings/go
zbridge targets                                               # list target ids
zbridge --help
```

`--name` defaults to the input file's stem, so `--input src/zcounter.zig` needs
no `--name` at all. A stem that says nothing about the library — `c_api`, `api`,
`ffi`, `lib`, `root`, `main`, `exports`, `bindings`, `c` — is **rejected** rather
than guessed at, because the library name feeds the ABI hash, every generated
file name, the Go package and the Python package directory. Deriving it from the
enclosing directory would make the generated bytes depend on where the repository
happens to be checked out, so zbridge asks you to say what you mean instead.

The name must be a plain identifier: letters, digits and `_`, starting with a
letter or `_`, and not a Go or Python keyword.

`port` never shells out to `zig build-lib`. It writes a throwaway project that
calls `addPortStep` and drives `zig build` over it, which is what makes the two
front ends produce the same bytes.

**The CLI only supports self-contained inputs.** A named package import
(`@import("zigimg")`) can only be resolved by a build graph, and the
name → module mapping lives in *your* `build.zig`, which the CLI cannot read.
zbridge detects this and tells you to use the build integration. Relative
imports (`@import("digest.zig")`) are followed and work fine.

## Supported types

The allowlist is deliberately narrow: every entry is unambiguously ABI-safe in
all three languages. Anything outside it is reported as an error naming the
function, the parameter and the source text — never silently skipped.

| Zig | C | Go | Python |
| :--- | :--- | :--- | :--- |
| `void` | `void` | — | `None` |
| `bool` | `bool` | `bool` | `c_bool` |
| `u8` `u16` `u32` `u64` | `uint8_t` … `uint64_t` | `uint8` … `uint64` | `c_uint8` … `c_uint64` |
| `i8` `i16` `i32` `i64` | `int8_t` … `int64_t` | `int8` … `int64` | `c_int8` … `c_int64` |
| `usize` / `isize` | `size_t` / `ptrdiff_t` | `uintptr` / `int` | `c_size_t` / `c_ssize_t` |
| `c_int` `c_uint` `c_long` `c_ulong` … | the C type | sized Go int | matching `ctypes` |
| `f32` / `f64` | `float` / `double` | `float32` / `float64` | `c_float` / `c_double` |
| `*Handle`, `?*Handle`, `*const Handle` | `Handle*` | `type Handle struct` | `class Handle` |
| `[*]const u8` + `usize` | `const uint8_t*`, `size_t` | `[]byte` (in) | `bytes` / `bytearray` / `memoryview` |
| `[*]u8` + `usize` | `uint8_t*`, `size_t` | `[]byte` (out) | `bytearray` |
| `[*:0]const u8` | `const char*` | `string` | `str` |
| `*T` / `?*T`, T scalar | `T*` | extra return value | extra tuple element |

Notes:

* A `[*]`/`[*]const` pointer **must** be immediately followed by a `usize`
  length. The pair collapses into one logical argument. An unpaired many-pointer
  is an error, because its length would be a guess.
* A many-pointer as a *return* type is rejected: ownership would be undefined.
* `c_long` is 32-bit on Windows and 64-bit elsewhere. It is supported, but
  prefer `i64` when you mean 64 bits.
* Handle lifecycle comes from naming, not annotations. `*_{new,create,init,
  open,alloc}` returning `?*H` is a constructor; `*_{destroy,free,deinit,close,
  release}` taking one `*H` and returning `void` is its destructor. Missing or
  ambiguous destructors are warnings, not errors.

Not supported in v1: structs by value, `extern struct` pointers, callbacks,
error unions, `u128`, and `anyopaque` outside a declared `opaque {}`. Wrap those
in a narrower `export fn` shim.

## Writing a portable input

These are the rules that decide whether your library actually loads inside
somebody else's Go binary or Python process.

**One file is the API surface.** zbridge reads exactly the file you point it at.
Its relative `@import`s resolve normally, so your implementation can be spread
across as many files as you like — but every `export fn` and every `opaque {}`
must be declared in that one file.

**No libc by default.** A `-dynamic` musl build that links libc links musl
*statically into the `.so`*. Loading that into a glibc host process — which is
almost every Go and Python process — puts two libcs, two mallocs and two sets of
TLS in one address space. That can appear to work and then fail later. So the
default is no libc at all, which leaves the shared library with zero runtime
dependencies. If you genuinely need libc, pass `.link_libc = true` and the Linux
targets become `*-linux-gnu.2.17`, which is manylinux2014-compatible, instead of
musl.

**No macOS frameworks, no system libraries.** Anything you link against becomes
something the end user has to have. A dependency-free binary is the whole point;
keep the exported surface pure computation plus memory you allocate yourself.

**No panics reachable from an export.** A Zig panic unwinds into a host runtime
that has no idea what to do with it. Range-check your slices, handle `len == 0`
without dereferencing (a zero-length `[*]const u8` may be a dangling pointer),
and use wrapping arithmetic where overflow is possible.

**Pin your minimum OS versions.** The target table does this already
(`aarch64-macos.11.0`, `*-linux-gnu.2.17`) so binaries never silently require
whatever the build machine happened to be running.

### Targets

| id | Zig triple (no libc / libc) | Go | Python | file |
| :--- | :--- | :--- | :--- | :--- |
| `linux_x86_64` | `x86_64-linux-musl` / `x86_64-linux-gnu.2.17` | linux/amd64 | Linux / x86_64 | `lib<n>.so` |
| `linux_aarch64` | `aarch64-linux-musl` / `aarch64-linux-gnu.2.17` | linux/arm64 | Linux / aarch64 | `lib<n>.so` |
| `macos_aarch64` | `aarch64-macos.11.0` | darwin/arm64 | Darwin / arm64 | `lib<n>.dylib` |
| `macos_x86_64` | `x86_64-macos.11.0` | darwin/amd64 | Darwin / x86_64 | `lib<n>.dylib` |
| `windows_x86_64` | `x86_64-windows-gnu` | windows/amd64 | Windows / AMD64 | `<n>.dll` |

## Generated output

```
bindings/go/
├── go.mod                    # written once if absent
├── go.sum                    # yours: run `go mod tidy` once, then commit it
├── native/<target-id>/…      # the compiled libraries
├── embed_<goos>_<goarch>.go  # one per target; build tags embed only the matching one
├── loader_gen.go             # extract → cache → dlopen → ABI check
├── <lib>_ffi_gen.go          # raw purego bindings
├── <lib>_gen.go              # the idiomatic layer
└── <lib>.go                  # yours, written once, never touched again

bindings/python/<lib>/
├── _native/<target-id>/…     # the compiled libraries
├── _loader_gen.py            # platform detect → ctypes.CDLL → ABI check
├── _ffi_gen.py               # argtypes / restype
├── _gen.py                   # the idiomatic layer
└── __init__.py               # yours, written once, never touched again
```

**Generated code is never hand-edited.** Files ending in `_gen` are rewritten in
full on every run. Your own code goes in the separate file zbridge creates once
and then leaves alone — the protobuf/sqlc model. That is why regeneration after
adding an `export fn` can never clobber your work.

**Publishing the Go module: commit `go.mod` *and* `go.sum`.** zbridge writes
`go.mod` (once, if absent) but cannot write `go.sum`, because producing it means
resolving and hashing modules from the network — not something a code generator
should do behind your back. Run `go mod tidy` in `bindings/go` once and commit
both files. Without `go.sum` the module is not self-sufficient: `go vet ./...`
and `go build` fail inside it, and anyone who `go get`s it inherits the problem.
Re-run `go mod tidy` whenever the generated `go.mod` changes its purego
requirement.

**Per-platform embedding.** A single `//go:embed native/*` would put every
platform's binary into every user's executable. Build tags keep only the one
that matches, and an unsupported GOOS/GOARCH gets a clear "platform not
supported" error instead of a link failure.

**ABI checking.** The compiled library exports `<lib>_zbridge_abi_hash()` and
the generated bindings carry the same constant. A binding loaded against a stale
binary fails at load time instead of miscalling into it. The hash covers
function names and types only, so renaming a parameter or editing a doc comment
does not invalidate an already-built binary.

**Local override.** `<LIB>_LIB_PATH` points the loader at a locally built
library instead of the embedded one. Essential while developing.

## Known limitations

Real edges, documented rather than papered over.

* **Narrowing `--targets` leaves the old files behind.** zbridge never deletes
  anything from the output directory, deliberately — a generator that deletes
  is a generator that can delete your code. Drop a target and the previous
  run's `embed_<goos>_<goarch>.go` and `_native/<target>/` are still there;
  remove them by hand.
* **Ownership is inferred from names, not declared.** A function named
  `<x>_destroy`/`_free`/`_deinit`/`_close`/`_release` is taken as the
  destructor for the handle it takes; `_new`/`_create`/`_init`/`_open`/`_alloc`
  returning one is taken as a constructor. If your API uses other words,
  zbridge warns and generates a wrapper with no `Close()`. If several
  candidates match, none is folded into `Close()`; each is emitted as a method
  that consumes the handle. A handle returned by anything else is treated as
  borrowed: no finalizer in Go, no `__del__` free in Python.
* **Python: a handle can be closed mid-call by another thread.** `close()`
  itself is locked, so two threads cannot double-free. But a thread that has
  already read the raw pointer for a call in flight will still use it if
  another thread closes the handle in between. Closing that window means
  serializing every call on a handle; it is not worth the cost by default, so
  treat a handle as owned by one thread at a time.
* **One file, file scope only.** zbridge reads a single `.zig` file and only
  its top-level `export fn` declarations. Exports nested in a container, or
  made with `@export`, are reported as an error rather than ported — they
  would otherwise be in your `.so` but missing from the bindings. Exports in
  files you `@import` are invisible to it entirely.
* **The CLI cannot resolve named packages.** If your input reaches a
  `build.zig.zon` dependency, use the `build.zig` integration: only a build
  graph knows how `@import("foo")` maps to a module.

## Verification

```sh
zig build test                                    # unit, snapshot and golden tests
zig build                                         # the CLI builds
cd examples/zcounter && zig build port            # the end-to-end example
git diff --exit-code bindings/                    # regeneration is deterministic
cd go_test  && go vet ./... && go test ./...      # a real Go consumer
cd py_test  && python -m unittest discover        # a real Python consumer
```

CI runs all of it on `ubuntu-latest`, `ubuntu-24.04-arm`, `macos-14` and
`windows-latest`. Because `bindings/` is committed, any change to generated
output — text or binary — shows up as a diff in review rather than silently.
